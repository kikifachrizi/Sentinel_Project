# SENTINEL Firmware — Build & Flash Guide

How to set up, build, flash, and operate the SENTINEL firmware on a NUCLEO-H533RE.

> Most of this document is reconstructed from actual build output. Items marked **[verify]** should be checked against your local setup before publishing.

---

## Requirements

| Item | Version / Note |
|---|---|
| STM32CubeIDE | 2.1.1 or later |
| Toolchain | `arm-none-eabi-gcc` 14.3.rel1 (bundled with CubeIDE) |
| STM32CubeProgrammer | 2.22.0 (bundled) |

## First-Time Setup

### 1. Import the project

CubeIDE → **File → Open Projects from File System** → select the repository root.

Do not use *Import → Existing Projects* if the workspace path differs from the original — CubeIDE stores absolute include paths in `.cproject`, and they will need fixing (see step 3).

### 2. Verify the μT-Kernel BSP path

The build references `mtk3_bsp2` by absolute path. From the original build:

```
-I"/home/kiki/sentinel_ws/mtk3_bsp2"
-I"/home/kiki/sentinel_ws/mtk3_bsp2/config"
-I"/home/kiki/sentinel_ws/mtk3_bsp2/include"
-I"/home/kiki/sentinel_ws/mtk3_bsp2/mtkernel/kernel/knlinc"
```

If your checkout is elsewhere, update these under
**Project → Properties → C/C++ Build → Settings → MCU GCC Compiler → Include paths**.

### 3. Confirm the `-Os` override on `sentinel_model.c`

**This is the single most important build setting.** The generated model compiles to roughly 610 KB at `-O0` and will not fit in 512 KB of flash. At `-Os` it is 145 KB.

To check or set it:

1. Right-click `application/lib/sentinel_model.c` in Project Explorer
2. **Properties → C/C++ Build → Settings**
3. Tick **Enable resource specific settings** if not already ticked
4. **Tool Settings → MCU GCC Compiler → Optimization**
5. Set **Optimization level** to `Optimize for size (-Os)`
6. Apply and Close

Verify it took effect — build and check the console. The line compiling `sentinel_model.c` must show `-Os`, while every other file shows `-O0`:

```
arm-none-eabi-gcc "../application/lib/sentinel_model.c" ... -Os ...
arm-none-eabi-gcc "../application/app_main.c"          ... -O0 ...
```

This setting is stored in `.cproject`. If that file is not tracked in version control, a fresh clone will build at `-O0` and fail at link time with:

```
region `FLASH' overflowed by 188008 bytes
```

## Build Configuration

These flags come from the actual build. They are listed for reference — CubeIDE sets most of them from the board selection.

### Compiler

```
-mcpu=cortex-m33 -std=gnu11 -g3
-DDEBUG -D_STM32CUBE_NUCLEO_H533_ -DUSE_HAL_DRIVER -DSTM32H533xx
-DsN_INTVEC=N_INTVEC
-ffunction-sections -fdata-sections -Wall
-fstack-usage -fcyclomatic-complexity
--specs=nano.specs -mfpu=fpv5-sp-d16 -mfloat-abi=hard -mthumb
```

`-mfpu=fpv5-sp-d16` — the Cortex-M33 FPU is single-precision only. The model uses `double`, which is software-emulated. This was measured and found acceptable (0.54 ms inference); see the ML documentation for why it was left unconverted.

### Linker

```
-T"STM32H533RETX_FLASH.ld"
--specs=nosys.specs --specs=nano.specs
-Wl,--gc-sections -static
-u _printf_float
-lc -lm
```

`-u _printf_float` is required — several diagnostic commands print floating-point values.

## Building

**Project → Build All**, or `Ctrl+B`.

A successful build ends with a size report:

```
   text	   data	    bss	    dec	    hex	filename
 248872	   4008	  37224	 290104	  46d38	sentinel_ws.elf
```

| Metric | Calculation | Budget |
|---|---|---|
| Flash | `text + data` = 252,880 B (246.9 KB) | 512 KB — 48% used |
| RAM | `data + bss` = 41,232 B (40.3 KB) | 272 KB — 15% used |

To break down flash usage by object file:

```bash
arm-none-eabi-size -A -d Debug/application/lib/sentinel_model.o
arm-none-eabi-size Debug/sentinel_ws.elf
```

## Flashing

### Hardware setup

| Item | Setting |
|---|---|
| USB ST-LINK (CN1) | Connected to PC — required for flashing |
| Power jumper | **E5V** — board powered from external 5 V |
| External supply | Connected before flashing |

The E5V jumper and the ST-LINK USB connection can be used simultaneously. E5V selects the MCU power source; the ST-LINK interface is independent and still works for flashing and VCP.

### Flash from CubeIDE

**Run → Debug** (or the Run button) uses the ST-LINK GDB server. Expected output:

```
ST-LINK SN  : 0030002D3434511634313937
Board       : NUCLEO-H533RE
Voltage     : 3.28V
Device ID   : 0x478
Device name : STM32H533/523
NVM size    : 512 KBytes

Memory Programming ...
  Size          : 90.12 KB
  Address       : 0x08000000
Download verified successfully
```

Confirm `Download verified successfully` before testing. A flash that appears to succeed but silently runs old firmware is the most time-consuming failure mode — several debugging sessions during development traced back to an un-flashed board.

## Serial Interfaces

The firmware uses two independent UARTs.

| UART | Pins | Interface | Purpose |
|---|---|---|---|
| USART1 | PB14 TX / PB15 RX | CP2102 adapter | Commands from host, encoder/PID replies |
| USART2 | PA2 TX / PA3 RX | ST-LINK VCP | `CLASSIFY` push, debug monitor |

Both run at **115200 8N1**.

USART1 is the ROS2 control link. USART2 is transmit-only in practice — the firmware pushes classification output there, and nothing reads commands from it.

### Connecting a terminal

```bash
screen /dev/ttyUSB1 115200      # USART1 — commands
screen /dev/ttyACM0 115200      # USART2 — CLASSIFY stream
```

Exit `screen` with `Ctrl-A` then `K`, confirm with `y`. A leftover session holds the port and will block ROS2 bringup.

## Command Reference

All commands are sent over USART1, terminated with `\r`.

### Motion

| Command | Arguments | Description |
|---|---|---|
| `m <L> <R>` | ticks/frame | Set closed-loop velocity targets |
| `o <L> <R>` | PWM counts | Open-loop PWM, bypasses PID |
| `e` | — | Read encoder counts: `<encL> <encR>` |
| `r` | — | Reset encoder counters |

### Tuning

| Command | Arguments | Description |
|---|---|---|
| `p` | — | Dump full PID state for both motors |
| `u <Kp>:<Ki>:<Kd>:<Ko>` | integers | Override gains at runtime |
| `f <percent>` | 0–100 | Scale feedforward contribution |
| `s <motor> <dir> <start> <step> <end> <hold>` | — | Open-loop static sweep |

`p` output format:

```
left:  70 0 110 50 157 178 142 190
right: 70 0 110 50 146 155 100 201
```

Fields: `Kp Ki Kd Ko u_db_fwd kv_fwd u_db_rev kv_rev`

> Runtime overrides via `u` and `f` are lost on reset. The compiled-in defaults always return after a power cycle.

### Data collection

| Command | Arguments | Description |
|---|---|---|
| `d <pattern> <surface> <rep>` | 1–5, 0–3, any | Run one 4-second data collection pass |
| `g` | — | 10-second logging run with per-frame CSV |
| `h` | — | Same as `g` but silent — use this for timing measurement |

Each `d` run emits a `#config` line, 80 CSV rows, and a `DC_TIMING` summary:

```
DC_TIMING,run_id=1,n=80,min_ms=6.352,max_ms=6.358,mean_ms=6.355,
ina1_fail=0,ina2_fail=0,imu_fail=0
```

`ina*_fail` and `imu_fail` must all be zero. Non-zero means an I2C read failed twice in a row on that run.

Use `h` rather than `g` when measuring loop timing — `g` streams CSV per frame, and the UART traffic perturbs the timing being measured.

### Diagnostics

| Command | Description |
|---|---|
| `c` | Classifier status: voted class, vote history, DWT timing |
| `j` | INA219 diagnostic — register dump for both channels |
| `k` | IMU diagnostic — WHO_AM_I, config registers, live stream |

`c` output:

```
CLASSIFY,voted=0,votes=0:0:0:0:0,inferCount=3089,
featUs_min=2482,featUs_max=2502,featUs_mean=2502,
modelUs_min=507,modelUs_max=600,modelUs_mean=537
```

Timing statistics accumulate from power-on and are never reset, so `featUs_mean` is drawn from `inferCount` samples.

## Bring-Up Checklist

After flashing a fresh board, verify in this order.

### 1. Sensors respond

```
j
k
```

Both must report `HAL_OK` throughout. `k` should show `WHO_AM_I=0x68` and an `az` reading near 16384 with the robot level.

### 2. Gains are correct

```
p
```

Expected:
```
left:  70 0 110 50 157 178 142 190
right: 70 0 110 50 146 155 100 201
```

If these differ, either the board is running old firmware or a runtime `u` override is still in effect.

### 3. Motors turn in the right direction

Lift the robot off the ground first.

```
m 50 50     → both wheels forward, smooth
m -50 -50   → both wheels reverse, smooth
m 0 0
```

Reverse direction is worth testing explicitly — feedforward uses separate constants per direction, and a sign error only shows up here.

### 4. Loop timing is clean

```
m 50 50
h
m 0 0
```

Wait for the `PID_PERIOD` report:

```
PID_PERIOD,n=5663,silent=1,min_ms=49.984,max_ms=50.015,mean_ms=49.999
```

`mean_ms` must be 50.000 ± 0.01. A period near 60 ms means something is blocking inside the control frame.

### 5. Classifier is running

Drive the robot for a few seconds, then:

```
c
```

`inferCount` must be non-zero and increasing. Zero means `sentinelTask` is never being scheduled.

On USART2, `CLASSIFY` lines should appear roughly twice per second:

```
CLASSIFY,0,NORMAL,Kp=70,Kd=110
```

## Verifying Gain Scheduling

The `CLASSIFY` line reports `Kp` and `Kd` read from the live PID struct, so a changing value means the control loop is using new gains — not merely that the classifier changed its mind.

Stronger evidence comes from reading the gains back through a different task on a different UART:

```
p                          → left: 70 0 110 50 ...

[drive onto the loaded surface, wait ~3 seconds]

                           → CLASSIFY,3,LOADED,Kp=85,Kd=150   (USART2)

p                          → left: 85 0 150 50 ...
```

The second `p` is served by `comTask` on USART1, independent of the `sentinelTask` that made the change. It also confirms `Ki`, `Ko`, and the feedforward constants were left untouched.

The hysteresis is visible in the stream — the class changes first, gains follow five inferences later:

```
CLASSIFY,2,BANNER,Kp=70,Kd=110
CLASSIFY,3,LOADED,Kp=70,Kd=110    ← class changed, counter starts
CLASSIFY,3,LOADED,Kp=70,Kd=110
CLASSIFY,3,LOADED,Kp=85,Kd=150    ← 5 consecutive → gains applied
```

## Troubleshooting

### `region 'FLASH' overflowed`

The `-Os` override on `sentinel_model.c` is not active. See First-Time Setup step 3.

### Board flashes but behaves like old firmware

Check the console for `Download verified successfully`. If the build failed, CubeIDE may still launch a debug session using the previously flashed binary.

### `inferCount=0`

`sentinelTask` is never scheduled. Check task priorities in `app_main.c` — `comTask` must be at a **lower** priority (higher number) than `sentinelTask`, because it never enters a WAIT state on its own.

### Encoder counts drift with motors stopped

Loose encoder wiring. A floating input picks up switching noise from the motor driver and registers it as quadrature pulses. Re-seat the connector and check continuity on the ground line.

### Loop period is 60 ms instead of 50 ms

Something blocking was added inside the control frame. μT-Kernel quantises `tk_dly_tsk()` to the 10 ms system tick, so a frame that overruns by even a fraction pushes the period to the next tick boundary.

### Commands ignored while driving

UART receive is interrupt-driven with a 64-byte ring buffer. If bytes are still being dropped, check that `USART1_IRQHandler` is present and that the NVIC interrupt is enabled in `MspInit`.
